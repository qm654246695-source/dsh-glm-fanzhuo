|---|---|---|---|

## 两套会话存储（容易踩）

`glm-chat.mjs` 按运行方式分两条存储，互不干扰：

| 入口 | 目录 | 指针 | 索引 |
|---|---|---|---|
| 命令行直接跑 | `home/.chat/sessions/` | `.chat/current` | 无 |
| `--serve`（面板/群聊） | `home/.chat/panel/sessions/` | `.chat/panel/current` | `.chat/panel/index.json`（标题/置顶） |

- 会话 id 只允许**数字和横线**（如 `20261019-2300`）。
- `/send` 带 `session` 时，只要那个 jsonl 存在就认，不会改面板的 current；
  但实测 current 被带跑过一次——**直接改 `.chat/panel/current` 文件**就能复原（serve 每次读文件）。
- `index.json` 不能带 BOM，否则读不到标题，会退化成用第一句话当标题。

## 饭桌怎么决定谁说话

1. 用户发言不 @ 任何人 → 三名成员**按轮转顺序**依次接话（每轮换先手，避免固定某位永远垫底）。
2. `@名字` → 只有**第一个**命中的成员回（想点两个人就分两条发）。
3. 页面底部「喊一声」→ `POST /nudge {"member":"glm"}`，单独让某位插一句。
4. 每次发言都会把最近 40 条记录 +「最新话题 + 你上一条说过什么（别重复）」塞进上下文。
   GLM 走 `local` 时只塞最近 **12** 条（9B 上下文小、转录越多越慢；实测 8 秒能答）。

## 她的眼睛和信箱

- **眼睛 = `read_image`**：按文件魔数认 PNG/JPEG/GIF/BMP/WEBP（不信扩展名），>10 MB 直接拒，
  路径走 `safePath` 围栏（只能读 `home` 树内）。工具返回 `{__image,mime,base64}`，`turn()` 再包成
  视觉内容块喂模型。**关键：base64 只进请求，不落 jsonl** —— 落盘的是 `已读图：路径（mime）`
  这一行短文本。否则会话文件会涨到 MB 级，而且每一轮都把整张图重喂一遍。
- **信箱 = `home/outbox/*.md`**：她写不了群聊的 `room.jsonl`（围栏不让），所以给她开了个投递口——
  往 `outbox` 丢一个 `.md`，`server.mjs` 每 2 秒扫一次，以「GLM」身份贴到饭桌上，然后把它挪进
  `outbox/sent/`。实测 4 秒上桌。这是「主动开口」的唯一通道，不用破围栏。

## 服务怎么活着

```
登录 → 启动文件夹快捷方式 → watch-services.ps1（隐藏窗口，单实例）
        每 20 秒探 11434 / 41300 的端口
        每 10 轮（约 3 分钟）再发一次「1 token 的极小生成」确认模型真的会答
        掉线 → wscript services.vbs → 隐藏拉起两个服务（60 秒冷却，避免重复起）
```

- **端口活着 ≠ 服务活着**：9B 会「假活」——`/health` 照回 200，但所有生成请求永远不响应
  （生成被中断过一次之后）。只探端口的看门狗会一直报 `ok`，永远不会救它。所以加了极小生成探活：
  连续两次失败、且面板不在生成（`41234/health` 的 `busy` 为空）→ 杀掉 `local_glm_server.py` 重拉。
- 杀进程前会核对 PID 的命令行里有 `local_glm_server`，并排除自己与父进程——不会误杀别的 python。
- **演练**：`watch-services.ps1 -Drill` 会真的杀掉 9B、重拉、并证明能生成（约 30 秒无服务）。
  **只在没人跟 GLM 说话时跑**。`-Once` 是只读自检（探端口 + 生成，不动任何进程）。
- **单实例判断的坑**：一个只是「命令行里提到了这个脚本」的 shell（比如 DSH 的 pwsh 工具用
  `-Command "...watch-services.ps1..."` 调它）也会匹配上，导致新看门狗把自己当重复实例秒退，
  服务就没人看管了。判断时必须排除 `-Command` 形式。
- `schtasks` 在本机被系统拒绝（`Access denied`），所以用启动文件夹 + VBScript 隐藏启动。
- 手动拉起：双击 `group-chat/services.vbs`（不弹窗）。
- 看门狗日志：`group-chat/watch-services.log`（不入仓库），心跳行会带探活结果（`gen ok`）。

## 后端的三种模式（纯本地要小心）

| `home/.chat/backend` | 行为 |
|---|---|
| `local` | **纯本地**：只用 11434 的 9B；失败不兜云端，直接报错。群聊里 GLM 的 `route` 也要写 `local` |
| `cloud` | 只用智谱云端 |
| `auto` | 按长度/关键词分流，失败互兜（旧行为，代码仍在） |

面板每 30 秒对账一次。**纯本地下最容易踩的坑**：9B 重启/加载那几十秒里，旧逻辑会判定
「本地不可达」→ 杀掉 local 的 serve → 拉起一个 cloud 的 serve，既违背「纯本地」又把在途对话掐断。
现在的规则是：配置要 local、现有服务也是 local 时，**保留它不换人**，等 9B 回来
（面板日志会写「本地 9B 暂时不可达，保留现有 local 服务」）。

## 三个会让人白熬一晚的坑

1. **思考型模型只思考不出正文**：GLM 5.3 系列给多少 `max_tokens` 就往 reasoning 烧多少。
   `glm.mjs` 内置三轮重试（原样 → 加长 → 8192 + 降 effort）；`reasoning_effort` 只认 `low|high|max`。
   `thinking:{type:"disabled"}` 对 5.3 系列无效（HTTP 400 `1210`），对 4.6/5.2/5-turbo 有效。
2. **GLM 的工具调用是文本 XML**：`<tool_call>name<arg_key>…</arg_key><arg_value>…</arg_value></tool_call>`。
   `local_glm_server.py` 负责把它解析回标准 OpenAI `tool_calls`，否则面板的 agent 循环看不懂。
3. **PowerShell 5.1 的编码**：发中文 JSON 要写文件再 `curl --data-binary "@file"`（连变量传都会丢）；
   `Out-File -Encoding utf8` 带 BOM，服务端要 strip；给人读的 `.ps1` 存 UTF-8 with BOM，
   给机读的 `package.json` 存 UTF-8 **无** BOM（DSH 宿主 `JSON.parse` 见 BOM 就崩）。
